# Monada Storage and I/O Design

## Purpose

Guide storage changes so Monada remains local, embedded, inspectable, and safe to evolve.

Use this skill for:

- `atoms/segment-*.log` changes.
- `vectors/segment-*.f32` changes.
- `indexes/*.idx` changes.
- `feedback/*.log` changes.
- `manifest.json` changes.
- compatibility, migrations, rebuilds, or rejection of incompatible stores.
- read/write path refactors.

## Required context before editing

Inspect:

1. `README.md` disk layout, Java API, and compatibility notes.
2. `monada-storage` implementation.
3. `monada-api` open/options behavior.
4. `monada-core` atom/vector model.
5. tests that open existing stores or read legacy rows.
6. recent PR feedback about vector encoding compatibility.

## Storage principles

- The storage format must be simple enough to inspect manually.
- The write path should be append-first and recoverable.
- The read path should validate manifest and file consistency.
- Legacy readable formats must remain readable unless an Issue explicitly removes support.
- New format semantics must be represented in metadata.
- Rebuild/migration should be explicit, not accidental.
- Errors should name the incompatible field, expected value, and actual value.

## Manifest rules

When changing any persisted semantic, consider whether the manifest needs new metadata.

Examples of metadata-worthy changes:

- vector dimensions.
- vector type.
- encoder name.
- encoder version.
- lexical expansion options.
- vector weighting options.
- quantization options.
- index format version.
- feedback query-key strategy metadata.

If a persisted vector cannot be safely compared with a newly encoded query, the store must either:

1. continue using the original compatible encoding;
2. rebuild vectors explicitly;
3. reject opening with a clear error.

## Append-only log guidance

For atom logs:

- preserve one logical atom per line unless the Issue explicitly changes segmentation.
- keep content and aliases safe for line-based parsing.
- maintain legacy five-field reads where currently supported.
- add tests for tabs, newlines, unicode, empty aliases, and malformed rows.

For feedback logs:

- keep original query text.
- keep derived query key when ranking uses one.
- preserve legacy events without `queryKey` by treating query key as equal to query.
- aggregate feedback deterministically.

For vector files:

- validate exact byte length where possible.
- ensure dimension mismatch is detected before search.
- avoid partial writes being accepted as valid vectors.

## Read/write path boundaries

Do not combine storage refactors with ranking changes unless the Issue explicitly requires both.

A storage PR should answer:

- What persisted format changed?
- What compatibility path exists?
- What happens to existing stores?
- How does a user rebuild or migrate?
- What tests prove old and new behavior?

## Acceptance checklist

A storage change is acceptable only when:

- README or format docs are updated.
- manifest semantics are explicit.
- legacy compatibility is tested or intentionally rejected.
- corrupted/truncated data is tested where practical.
- no ranking change is hidden inside storage loading.
- no external database is introduced for the MVP path.
- `MonadaMemory.open(path)` behavior remains predictable.

## Anti-patterns

- Silently re-encoding existing atoms during open.
- Mixing vectors generated by incompatible encoders.
- Changing defaults without manifest validation.
- Replacing simple files with a database dependency before the project needs it.
- Making files unreadable without providing a diagnostic tool or clear documentation.
